# 请求采集

请求采集默认关闭，只采集当前应用实例经过的流量，不是全站分布式采集服务。
认证头和结构化凭据字段在落盘前脱敏；自由文本仍可能包含对话、工具参数和粘贴的凭据。
只有 ID1 可管理，查看正文或导出还需当前管理员会话最近 5 分钟内完成 2FA。

## ID1 八小时诊断

后台「诊断与运维 → 请求采集」提供独立的 ID1 持续诊断开关，默认关闭，
配置字段为 `request_capture_config.id1_diagnostic_enabled`。
开启后只匹配通过站内 API Key 鉴权的用户 ID 1，不根据客户端自报的用户头判断。
成功、失败、重试以及工具续轮都进入采集，涵盖 HTTP、SSE 和 WebSocket 的入口、
出站、上游响应与下游响应；它不要求同时开启普通定向采集。

每条记录从首次采集起保留八小时，包含正文文件和索引；仍在运行的长请求也不延长
保留期。开启的是持续采集，而不是八小时后自动关闭开关。关闭后不再接收新记录，
保留中的历史仍可读取，直到各自到期。已收尾的单条记录可以在持续任务运行时导出。

资源保护仍然生效：单条记录最多 128 MiB、进程采集缓冲最多 64 MiB、同时采集最多
256 个请求、最多保留 100000 条专用诊断记录，另受配置的磁盘配额约束。
达到限制时不中断业务请求，页面显示跳过计数和截断原因，因此不能将采集开启等同于
无限制或绝不丢包。认证头和结构化凭据字段仍然脱敏。
专用诊断保留可安全解析的媒体正文，签名 URL 继续脱敏；无法解析的类型按已有规则
省略并注明原因。这是应用层内容对照，不是逐字节网络 pcap。

## 每个蓝绿槽位必须有稳定身份

为需要采集的应用实例设置 `SUB2API_CAPTURE_INSTANCE`，例如 `gateway-blue` 或 `gateway-green`。
同一主机上并行运行的槽位必须使用不同值；同一槽位重启沿用原值，并保持 `DATA_DIR` 持久化。
未配置时不创建采集存储，也不能通过后台开关启用；这不会阻止模型网关启动。
采集数据位于 `DATA_DIR/request-captures/<slot>`，不应挂为网站静态目录，不得提交版本库。
独占文件锁避免两个进程同时打开同一槽位；重复槽位初始化失败，原进程继续采集。

## 管理入口必须固定到实例

后台会显示当前实例 UUID，并对之后的管理调用发送 `X-Capture-Instance`。
若负载均衡转发到另一实例，返回 409；不会显示另一实例的空任务或修改其内容。
请通过已经鉴权的同源管理入口将采集页面固定到目标实例，或在现有负载均衡配置中安排管理粘性。
该功能不会自行修改 nginx、DNS 或生产路由，也不会跨主机代理管理请求。

## 重启与保留期

同一槽位重启后可读取原有已确认错误记录，以及八小时内已收尾的 ID1 诊断记录。
普通定向任务标记为中断，不自动恢复；ID1 持续诊断按独立开关恢复。
临时或未收尾残留由该槽位启动恢复清理；普通已结束任务按配置保留期清理，
ID1 诊断记录始终按各自八小时期限清理。
永久退役槽位时，应先停止采集、按需导出并删除任务，再停止该实例；退役后无人运行的槽位不会自动执行 TTL。
早期试验若遗留 `pid-*` 目录，请在核实无活跃进程并按本地数据保留制度处理后清理；程序不会猜测并递归删除其他槽位。
