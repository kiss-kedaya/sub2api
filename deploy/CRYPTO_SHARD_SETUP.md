# 加密钱包分片（数据密钥 / Shamir 2-of-3）运维与恢复

本文件描述 `crypto.signer.vault` 的「数据密钥 + 分片」模式：部署、恢复、回滚与风险边界。
代码入口：`backend/internal/cryptopay/wallet/shards_vault.go`、`backend/internal/cryptopay/wallet/shards/`。

## 1. 它解决什么

改造前：vault 用 `TOTP_ENCRYPTION_KEY`（安装密钥）直接加密，密文和密钥都在服务器/同一个库里，拖库或拿到服务器环境即可解密母钱包种子。

改造后：

- `settings.crypto.signer.vault` 改为 `sub2api-wallet:v3:` 密文，密钥是 **32 字节随机数据密钥 DK**。
- DK 用 **Shamir GF(256) 2-of-3** 拆成 3 份（格式见下）：
  - **A = 服务器**：用安装密钥经 HKDF-SHA256 派生密钥加密后存 `settings.crypto.signer.vault.shards`。
  - **B = 老板手机**：浏览器生成，只展示一次，**不发送给服务器**。
  - **C = 离线纸质备份**：同上，只展示一次。
- 服务器只保存 A（以及公开的 DK 承诺值 `SHA256("sub2api/crypto-wallet/dk-commitment/v1:" + DK)`）。
- 单独拖库/拿到服务器：只有 A，解不开。必须再有一份人工持有的分片。

### 威胁模型与已知边界

- 默认路径（A）：**迁移窗口**内服务器在内存中同时存在旧安装密钥、旧 vault 明文和新 DK；这是一次性窗口，审计记 `signer_shards_setup`，DK 用后立即清零、不落盘、不写日志。该窗口无法完全避免（旧 vault 本来就能被服务器解密）。
- 严格路径（C，可选，本次未实现/未默认启用）：浏览器/离线环境生成**全新钱包**，旧地址资金用旧助记词在本机离线逐笔签名扫尾，服务器全程不接触任何明文。代价是换钱包 + 旧地址逐个签 + 操作复杂。仅在怀疑泄露时作为人工轮换流程使用，不阻塞本次上线。
- 自动归集开启后，服务器同时持有 A 和 `B_auto`（= 操作员分片的加密副本），等价于「服务器可无人值守解开」。这是显式接受的风险，仅建议小额热钱包；关闭自动归集会删除 `B_auto`。
- 服务器被完全控制且操作员正在执行归集时，内存中的单把私钥仍可能被读走——分片方案保护的是**静息数据**，不是运行时。

## 2. 分片格式（S2V1）

- 方案：`shamir-gf256`，GF(256)，约简多项式 `0x11b`，生成元 `0x03`；阈值 2，总数 3。
- 文本：`S2V1-XXXX-XXXX-...`，`S2V1` 前缀 + RFC 4648 base32（无 padding）按 4 字符分组；解析时忽略空格/换行/连字符，大小写不敏感。
- 解码后的 payload：

  | 字段 | 长度 | 说明 |
  | --- | --- | --- |
  | version | 1 | 当前 1 |
  | threshold | 1 | 2 |
  | total | 1 | 3 |
  | index | 1 | 1..3 |
  | dataLen | 1 | 32（DK 长度） |
  | data | dataLen | share y 值 |
  | checksum | 4 | 前面所有字节 SHA-256 的前 4 字节 |

- 每个字节 `s` 生成一次多项式 `f(x) = s + a1*x`（a1 随机），第 i 份 share 取 `f(i)`。任意 2 份在 x=0 处 Lagrange 插值可还原 32 字节 DK；1 份不含任何 DK 信息（信息论安全）。
- DK 承诺值用于防止「格式合法但属于别的钱包」的分片：合成结果 `SHA256(域前缀||DK)` 必须等于服务器保存的承诺值。
- 服务端合并前先做 checksum，任一字符错误直接拒绝；错误提示统一为“分片无效”，不暴露“接近正确”的信息；连续 5 次失败锁 15 分钟（按审计表滚动窗口计数，多实例共享）。

## 3. 初始化（浏览器生成分片）

前置：管理员已登录、已绑定 2FA、加密支付通道已初始化（v2 vault 已存在）。**先做完整数据库备份。**

1. 打开后台「加密支付 → 签名分片」页。
2. 浏览器 WebCrypto 生成 32B DK；本地做 2-of-3 拆分；计算承诺值。
3. 页面弹阻断式风险提示；必须输入后端下发的风险确认短语（中文或英文，后端常量校验）。
4. 输入当场 2FA 验证码（不是 5 分钟 grant）。
5. 浏览器把 `DK`（仅此一次）、`share_a`、`dk_commitment`、以及**回填的一份分片**（B 或 C）提交给服务器。
6. 服务器在**一个事务**里：用安装密钥解旧 v2 vault → 重新用 DK 封装成 v3 → 保存 share A（安装密钥加密）+ 承诺值 + 公开的热钱包地址 → 审计 `signer_shards_setup` → 提交。
   - 提交前会校验回填分片与 A 合成出的 DK 一致、vault 可解密、现有充值地址仍能从种子推导。
   - 校验失败不落库，旧 v2 vault 原样保留。
7. 页面只展示一次 B、C（二维码 + 文本 + 下载/打印）；随后服务器在内存窗口内预生成一批充值地址（当前 500/链族），因为锁态下无法再派生新地址。
8. 关闭页面后不可再查看 B、C。

## 4. 日常操作

- **手动归集**：输入分片 B（或 C）→ 服务器 A+B 合成 DK → 只解本笔需要的私钥 → 签名 → 立即清零。分片不落库、不进日志/审计 detail。
- **导出助记词 / 导出单地址私钥 / 更换 Gas 助记词**：同样需要输入一份分片。
- **重新拆分**：用任意 2 份还原 DK（浏览器本地），重新生成 3 份新分片；把新 A + 新回填分片提交，服务器校验 DK 承诺值一致后原子替换 A，旧分片全部作废，`B_auto` 一并清除。
- **自动归集**：默认关。开启需当场 2FA + 风险短语 + `acknowledge_risk`，服务器保存 `B_auto`；之后每小时自动归集只在小额热钱包场景使用。关闭自动归集会删除 `B_auto`。**进程重启后锁态丢失是设计目标**：没有 `B_auto` 时自动归集不会运行。

## 5. 恢复步骤（服务器或数据库仍可用）

1. 从管理员处取任意 2 份分片（B/C，或 A 可从服务器导出——仅导出加密后的 A 没有意义，通常用 B+C）。
2. 按第 2 节格式解码两份分片，校验 checksum。
3. 在离线环境用 GF(256) Lagrange 在 x=0 插值还原 DK，并核对 `SHA256("sub2api/crypto-wallet/dk-commitment/v1:"+DK)` 与 `settings.crypto.signer.vault.shards.dk_commitment` 一致。
4. 用 `AES-256-GCM(DK)` 解密 `settings.crypto.signer.vault`（`sub2api-wallet:v3:` 后 base64；nonce 在密文前 12 字节，AAD 为 ASCII `sub2api-wallet:v3:`），得到 `{"deposit":"...","hot":"..."}`。
5. 若服务器仍在：直接把任意一份分片在后台「验证分片」或归集页输入即可，无需离线操作。

**B、C 两份都丢失 = vault 永久不可解**，任何服务器权限都无法恢复；这是设计约束，生成页会强提示并在风险弹窗中确认。

## 6. 回滚

- 初始化事务失败/校验不通过：无需回滚，旧 v2 vault 未被修改。
- 已迁移成功但需要退回 v2（不推荐，安全性倒退）：
  1. 停止服务；
  2. 从迁移前数据库备份恢复 `settings`（含 `crypto.signer.vault`、`crypto.signer.vault.shards`）；
  3. 确认部署环境仍有原 `TOTP_ENCRYPTION_KEY`；
  4. 启动并验证 2FA/钱包。
- 不要通过删除 shards 行来回滚：删除后 v3 vault 将没有任何密钥路径。
