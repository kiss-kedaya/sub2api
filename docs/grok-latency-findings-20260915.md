# Grok 首字延迟排查记录（2026-09-15）

## 结论与范围

本轮确认短请求也会产生上游 reasoning，且正文晚于 reasoning 到达；没有证据证明网关将正常正文一直积攒到 EOF。也不能把公网观察到的 12–16 秒正文首字全部归因于上游思考。公网耗时与 DB 转发耗时存在尚未定位的差额。

对象为 0.1.312 的 Grok 4.6 流式请求。先在独立工作树以延迟分块 httptest 验证，再在获准范围内只读查询测试 usage 和对应账号配置，并做一次公网网关、一次同账号直连上游的极短 Chat 对照。没有扫描号池、修改生产配置或数据库记录。对照请求本身会产生正常推理消耗；网关请求的 usage 已核对。

本文不保留凭据、请求正文、账号标识或上游域名。以下“上游 A/B”仅区分本轮实际选中的两个账号。

## 公网与 DB 计时不能混用

| 指标 | 实际含义 | 不能据此推断的内容 |
| --- | --- | --- |
| 公网 headers | 从客户端发起 HTTP 请求到响应头返回 | 不等同于上游模型开始输出 |
| 公网首 reasoning / 首 text | 从同一客户端起点到读到非空 reasoning / 正文事件 | 两者都包含入站链路及网关转发前等待 |
| DB `first_token_ms` | 成功转发路径内部计时，具体结束条件随协议而异 | 不是统一的客户端正文首字 |
| DB `duration_ms` | `OpenAIForwardResult.Duration`，即转发路径内部耗时 | 不包含完整公网往返，也不代表所有选号等待或失败尝试总耗时 |

现场 `openai_ttft_mode=semantic`。Responses 跳过 preamble 后按语义事件计时，reasoning 可以先触发；修复前 Chat/Responses 和 Messages/Responses 转换按首个 data payload 计时，可能命中 `response.created`。raw Chat 原有统计也可能命中 role-only 等非正文 chunk。

`visible` 口径也不能直接称作“正文首字”：现有判定包含非空 reasoning、工具参数等输出。要比较实际阅读体验，必须单独记录 `first_text_ms`。

三条均为 HTTP 200，usage 已落库，实际请求的 `upstream_model` 均为 `grok-4.6`。公网总耗时原始记录保留两位小数，因此可能略小于毫秒精度的首 text。

实际配置与影响：

- A/B 均为 `platform=grok`、`type=apikey`，配置自定义 HTTPS 上游，无账号代理；并非官方 OAuth 账号。
- 两者模型精确映射均为 `grok-4.6`，未配置账号级默认 reasoning effort。
- 全局默认上游模式为 `cli`，但显式账号地址优先，本轮请求不因此改走官方 CLI 上游。
- Messages 转 Responses 在调用方未指定 effort 时默认注入 `medium`，DB 也记录为 `medium`。
- 这批 Responses、raw Chat 请求未指定 effort，DB 为 null；null 不表示关闭思考，实际行为由上游决定。
- 输入及缓存 token 明显不同，三条协议的负载并不等价，不能用其耗时排序证明某种转换更快。

现场 312 与此前 303 的 p95 请求负载同样不同；分位数变化不能单独归因于版本修复。

## 同账号直接上游对照

另做一组极短 Chat 请求。公网请求实际选中已查过的上游 B，再用该账号已有配置直连同一上游。两次请求使用相同模型和请求参数，未指定 effort，启用流式 usage；不记录请求正文。

| 路径 | headers / 首 reasoning | 首 text | 完成 | 输入 token | reasoning token |
| --- | ---: | ---: | ---: | ---: | ---: |
| 公网网关 | 2.890s | 5.093s | 5.265s | 211 | 102 |
| 直接上游 | 3.860s | 4.813s | 4.875s | 211 | 55 |

两次均为 HTTP 200，上游回显模型均为 `grok-4.6-build`，均返回 usage。网关 usage 的 DB 首输出为 2.055s、转发耗时为 4.277s；输入 83 加缓存读取 128 对应上游输入 211，输出 103 对应正文 1 加 reasoning 102。

这组证据说明：

- 绕过网关后，上游仍有数秒等待并输出 reasoning，确认存在上游思考耗时。
- 本次两条路径正文首字相近，未复现秒级正文积攒；不能据此排除其他请求或其他部署链路的等待。
- 两次都是从本地发起，直连路径没有经过网关主机；网络路径、缓存命中和采样生成不同，不构成严格的处理耗时差分。不能把 0.280s 差值当作网关开销。
- 对照显式使用 `Accept-Encoding: identity`，原始 smoke 未固定该编码。不能排除编码或中间代理对历史现象的影响，也没有证据认定它们是根因。
- 单组结果不是性能基准，不能外推到 p95、长上下文、多并发或另一上游。

## 统计修复与实际提速分开验收

独立分支提交 `b500fe653675658f80fd39b411b4ab68bd2f4692` 包含最小修复和延迟分块测试：

- 修复前，上游先发 `response.created`，80ms 后才发正文，Chat/Messages 转换的 `FirstTokenMs` 仍约为 0ms。修复后 Grok 转换复用现有 `semantic/visible` 口径，跳过 preamble。这是统计修正，不会让上游更早生成正文。
- Grok Responses 已将文本事件 flush 给客户端，但完整终止事件后仍等待 EOF；raw Chat 在收到 `[DONE]` 后也继续等连接关闭。测试在终止帧后保持连接不关闭，修复前两条在 2 秒内均未返回。
- 修复后上述终止收尾测试通过，避免已结束请求继续占用转发流程；这不等于降低当前请求的正文首字。
- 本地 Grok Responses 测试包含 billing ping filter 与客户端工具恢复包装器，首个完整文本事件在终止前已 flush。raw Chat 同样验证了首个文本的 flush，且终止前的输入、输出及缓存 usage 保留。
- 4 个定向用例先红后绿；随后已有 Grok 与 Responses flush 相关定向测试通过，未运行全量测试。Chat/Messages 新增用例主要证明计时口径及终止返回，不足以声称所有公开入口、工具流和部署链路均无缓冲。

提交后的复核还提出 `[DONE]` 缺最终 usage、同步扫描终止以及更完整 EOF 边界验证；本轮在要求停止扩大后未补入上述提交。合入方应结合后续终止与生命周期补丁验收，不能把本提交视为所有流边界均已覆盖。

## 未定位差额与排查经验

三条旧公网测试的总耗时分别比 DB 转发耗时多约 7.857s、9.185s、9.510s。该差额不是已证明的网关缓冲耗时，也不能只算作选号排队。首输出与总耗时差额不能用一个固定偏移完全解释。

当前缺少同一请求在鉴权、选号/抢槽、失败重试、上游首语义事件、下游 flush、代理出站及客户端接收之间的完整时序。DB 保存的是成功转发的局部计时，公网测量覆盖更长路径；没有逐段证据，无法分配上述差额。

后续若继续定位，应先用同一请求标识对齐已有逐段诊断，保留首 reasoning、首 text、完成三个时间点，并对齐账号、协议、输入及缓存 token、effort 和响应编码。已有证据不足时，结论应保持“未定位”，不要仅因耗时长就猜测缓冲，也不要仅因收到 reasoning 就认定全部等待来自思考。
