# 高频路径并行审查

日期：2026-09-16。基线main `5a2f3f89c`，生产319源码 `0f71bd64c`。
本轮按请求解析、协议用量、生命周期、选号缓存四组建立独立工作树；主代理复核请求读取和错误日志。
子代理不访问服务器、生产API或数据库。所有发现必须先有构造复现或基准，再决定是否合并。

## 主代理已确认

### 压缩请求被静默截断

- `internal/pkg/httputil/body.go` 在gzip、deflate、zstd解压后以LimitReader限制64MiB，没有多读一字节确认超限。
- 修前：大于上限的压缩请求得到无错误的64MiB前缀。前缀若是合法JSON加空白，后续内容被忽略。
- 刚好64MiB且校验和损坏时，三种压缩格式均可能在读取校验尾部之前被LimitReader提前结束，错误被吞掉。
- 两类边界测试在旧实现全部失败；修复改用标准库MaxBytesReader，保留原来的io.ReadAll。超限通过现有errors.As路径映射为413，损坏编码继续走读取失败。
- 正常大小和恰好上限的合法内容保留；失败不更新Content-Encoding/Content-Length。httputil全包与race通过。
- 历史来源：`40feb86ba`已有该逻辑，不是319新增。
- 试验过复用分块读取降低解压分配，但1MiB分配从约2.27MB升至3.19MB、8MiB时延变差，因此未保留。
- 最终基准不是性能优化：1MiB约0.44ms、8MiB约3.5--3.7ms，分配基本保持，仅增加一个小包装分配。换取完整超限与校验检测，不宣传提速。

### 错误日志截断后仍保留大请求头

- `normalizeOpsPersistentUserAgent` 把User-Agent截至512字节，但Go子串保留原始字符串存储。大量空白被TrimSpace移除时同样会保留。
- 修前：队列按512字节估算的字段仍可持有32KiB原请求头；并发错误或数据库迟缓时放大队列实际驻留。
- 构造32KiB头和两边长空白的短头，检查返回字符串是否仍指向原存储。旧实现失败。
- 修复只在异步入队边界Clone已经截短的字段，保持UTF-8清理和512字节上限。不会复制整条原请求头。
- 历史来源：`b92bbf0299`已有该逻辑，不是319新增。

### 鉴权共享等待无法取消（P2，已合并）

- 相同Key的首个查询未完成时，后续请求在singleflight.Do中等待；它们取消后也无法退出。首请求的取消又可能使其他正常等待者一起失败。
- 改用DoChan和各自context选择返回。共享查询使用独立5秒预算，不由某一个调用者取消；非共享分支保持原调用上下文。
- 5秒是新增的共享鉴权查询上限，使用鉴权专属常量，不依赖设置缓存常量，也不新增生产配置。极慢后端查询会更早失败，是后续上线需监测的行为边界。
- 已取消/等待中取消、首请求取消/截止、正常等待者仍收到同一个结果、查询失败后重试、超时释放查询配额及不写入无效Key缓存均通过。
- 错误类型保持：无效Key仍为401，查询槽位满为503，普通查询超时/数据库错误沿原中间件为500，不把超时伪装为无效凭据。
- 负载取消回归的放行栅栏同时改为Once+close，避免测试自身在后台提前退出时卡死。
- 历史问题自 `9d0a4f3d68` 鉴权缓存引入；代理 `0e2c9509e` 合并为正式 `3c28a33c5`。

### 工具schema字符串解码错误与重复扫描（P2/P3，已合并）

- 兼容层以Go字符串规则解码JSON字符串。JSON合法的转义斜线、UTF-16代理对被拒绝后，工具lookaround约束未清理，上游仍可能拒绝请求。
- 常规路径保持不变，仅字符串解码失败时回退标准库JSON解码；保留平台范围，Grok不套用OpenAI的lookaround清理。
- 普通历史消息已经在type probe完整解析，又按Skip再扫描一遍。复用同解析器的结束偏移，保留语法、深度、尺寸、编辑数、UTF-8与完整JSON检查。
- 六个修前失败用例修后通过，并扩展全部转义类别、重复type既有选择、125/126深度边界、实例值不改、非法JSON和原始偏移回归。88项定向race、两组模糊测试分别29281/31607次输入通过。
- 三轮局部基准中位数：1MiB无工具2.835ms到2.319ms（18.2%）；8MiB无工具24.668ms到18.417ms（25.3%）；8MiB修工具39.463ms到31.287ms（20.7%）。小请求场景也有约11%的改善。无新增正文拷贝。
- 这是实际调用的局部schema路径收益，不是整站/首字收益，也不是前轮独立原型的6倍。初版出现额外小分配，代理已消除后复测。

### 共享HTTP池关闭接口被包装层遮蔽（P2，已合并）

- GetClient返回的Client带校验/计时RoundTripper，包装器没有CloseIdleConnections，标准库公共方法静默无效。
- 本机httptest先确认连接复用，再调用关闭并等待服务端StateClosed：开启/关闭IP校验两种场景修前均失败。修后确实关闭空闲TCP，下次重新建连；活跃响应仍完整返回。
- 池内部小适配器保存原Transport引用，只转发空闲关闭，请求仍经过原校验/计时层；不新增每请求拷贝、后台任务或改配置。

- 当前共享池消费者未找到主动关闭调用；上游独立池/WS独立池的关闭对应未包装的Transport，不受此问题影响。因此不声称本补丁能单独解释或降低现网RSS。
