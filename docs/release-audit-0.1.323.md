# 0.1.323 流式超时与 Responses 必需字段修复

日期：2026-09-16。基于双机全量的 322。

## 已确认问题

- 真实上游账号 28659 返回顶层 `code=request_timeout` 的裸 `error`，内容为 `stream closed before response.completed`。此前未进入无输出故障转移，且裸错误没有登记最后 attempt，导致部分错误误归平台或沿用旧过载详情。原始证据见 `diagnosis-responses-stream-timeout-20260916.md`。
- 用户追加报告 `missing field sequence_number`。本地回归复现：协议转换首帧序号为 0 时被 `omitempty` 删除；HTTP/WS 合成失败和 compact 合成流也缺字段。旧 handler 注释及测试明确要求省略该字段，这与实际严格客户端不兼容，不能继续沿用。

## 修复边界

- 精确识别结构化 `request_timeout`，仅未提交输出且客户端仍在线时进入现有有界故障转移。没有扩大全局重试次数或默认原账号重试状态码。
- OpenAI Responses 的 APIKey 与 OAuth 统一使用已有裸错误终态处理。保留原错误码；有真实 `response.failed` 时采用真实终态，只生成一次失败；后续真实 completed/done 优先，`[DONE]` 不抹掉失败。没有伪造成功或用量。
- 最终失败复用既有 Ops 登记函数，保留最后账号/request ID/原始详情；关闭正文记录时清除旧详情。裸 error 与 failed 不重复记录，重复 failed 仅继续收集用量。
- 客户端取消后，不将读取错误误判为可重放失败，已知用量和缓存用量继续返回。成功恢复时清除旧错误的免计费标记，不修改价格、余额、预扣或数据库。
- Responses 事件序号 0 必须序列化。合成失败保留可获得的原序号，独立网关失败无原序号时使用 0；compact 输出项和 completed 连续编号。补齐合成失败 response 的 created_at。
- 复核发现并修正透传失败合成前的 keepalive 停止顺序，确保正式写出前结束并发心跳。

## 部署要求

- 候选 323 使用 8091/pprof 6070，原 322 的 8090 保持运行，旧连接自然结束。
- 复用已修正的探针规则和事务交接：1% 至少观察 180 秒且至少 50 次成功业务请求，之后才允许全量；全量至少监控 300 秒。
- 仅平台健康、应用存活和内存余量触发回退。上游业务 502/503 不作为自动回退依据，499 探针取消不视为平台失效。
- 新旧物理服务器份额保持旧 40%、新 60%。生产环境、nginx 配置先备份，数据库仅校验迁移。

## 后续排障经验

- 客户端的反序列化错误必须验证真实 JSON 字段存在，不能只把缺字段解码成 Go 零值后宣称正常。
- 顶层 `code` 与嵌套 `error.code` 都可能来自合法上游错误。错误分类应优先结构化证据，不能凭文案里的 timeout 开启重试。
- bare error 可能只是前导事件，最终 completed/failed 才权威。延迟副作用与错误登记能避免成功请求被标失败、重复扣减健康值或误免单。
- 完成事件修补不会让真实上游断流消失。已输出内容不能透明重放；仍需按真实最后 attempt 排查上游稳定性。
