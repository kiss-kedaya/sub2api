## 事故与实际修复

1. 新机 Nginx 每 worker 只有 768 个连接，实际文件软上限 1024。14:33 明确记录 `worker_connections are not enough`。14:45 将连接上限改为 4096、文件软上限改为 8192，备份后校验并平滑重载，应用 PID 不变。后续没有再观察到该上限错误。
2. 旧入口把上游业务 HTTP 502/503/504 计入整个聚合后端的失败次数。后端被暂时摘除后，两个备用地址仍指向已经没有应用监听的本机端口，导致 `no live upstreams`，连 `/health` 也 502。15:10 改为仅网络错误、超时和非法头触发代理重试，并替换失效备用地址。
3. 上述两项不是全部原因。随后仍观测跨机 TCP 建连 1--2 秒重传、偶发连接超时和 `/readyz` 503。内网 ping 约 0.1ms 不能排除 TCP 异常；Redis 本机 PING 为 0ms，跨机链路有重传。没有凭猜测修改网卡、sysctl、防火墙或数据库。
4. 此前所谓旧版 60% / 新版 40%，实际上是同一台机器内的两个版本。旧物理机只反代到新物理机，未分担应用计算。16:00 前后在两机分别启动 316；16:12 从 1% 开始，16:17 到 20%、16:21 到 50%、16:24 到 100%，新版本内部按物理机 60/40 分配。
5. 用户后来明确允许旧进程只留最近回退版本。16:12 平滑停止 303 两实例、313、315，16:16 均退出，保留 312；旧二进制和无效服务定义先归档后从活动目录删除，数据、环境文件和数据库备份保留。释放约 12GiB 旧实例内存。

## 流式与缓存验证

- 316 旧机直连 GPT Chat：首正文 3.306 秒，总 12.790 秒，257 个正文片段，67 个不同 100ms 时间段。缓存 4224 与账单一致。
- 316 公网 GPT Chat：首正文 5.409 秒，总 18.802 秒，260 个正文片段，78 个不同 100ms 时间段。缓存 4992 与账单一致。
- 316 公网 Grok Messages：首事件 2.500 秒，首正文 34.076 秒，总 40.212 秒，413 个正文片段。缓存 128 与账单一致。推理等待与正文生成需分别观察。
- Grok Responses、Chat 上游直连也观测到数百个实时片段；不能由少量异常样本推断整个分组完全失去流式。
- 同时确实存在少量 `first_token_ms` 与 `duration_ms` 相差不到 20ms 的记录，部分 Grok 集中于缓存 192、返回模型名没有 build 后缀的响应形态。仅属关联，尚未证明根因。输出 token 包含 reasoning，不能直接当作正文长度。
- 使用长回答、逐行读取、`Accept-Encoding: identity`、分别记录响应头/首事件/首推理/首正文/终止时间。只让模型回复 OK，正文只有两字，不能用于证明整个流式被缓冲。
