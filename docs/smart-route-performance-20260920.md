## 热点与改动

两台各采样 15 秒 CPU。旧机沿组路由累计 3.23%，新机对应采样约 2.8%；新机最大 CPU 热点仍是请求 JSON 处理。本次性能收益限于路由与模型目录，不能宣称整站或首字加速十余倍。

原实现先准备所有候选组，再执行选号。首组已能成功时，仍读取后续每组的九个平台目录。新增回归在旧实现上失败，证明未使用的备用组仍被访问九次。

- 共享候选迭代器按需准备分组；已确认支持模型且选号成功后立即结束。
- 遇到未知目录时继续向后查找已确认支持模型的授权组，并保留原有优先顺序。即使已知支持的组选号失败，也不把未知组重新放行。
- 分组权限、active 状态、白名单、候选组模型映射仍在目录读取与粘性选号之前执行。
- 保留完整实际计费组、倍率与 composite 父组身份，不修改结算、预扣、退款代码。
- 模型目录直接遍历已有账号，使用账号原有的原子模型映射缓存，消除按平台筛选时的整份账号数组复制。
- 不增加长期缓存，不放宽 snapshot-only，不把目录冷启动变成同步数据库扫描。

## 经验

- 优化候选遍历必须同时保留未知目录与明确不支持模型的区别，不能单纯遇到一个可用账号就提前绕过目录优先规则。
- 账号模型映射已有原子缓存，重复复制账号会丢失缓存复用机会；先复用现有机制，再考虑增加缓存或更换库。
- 微基准需同时覆盖首组命中与全组失败重试，单看最佳路径会掩盖尾部退化。
- 结算审计使用数据库状态的实际类型和索引，生产查询必须只读、限时；不能凭测试状态名猜数据库枚举。
- 本机测试、源码 CI、发布物校验、线上实际路由和真实账单是不同层次的证据，必须分别记录。
- 灰度 promote 统计的是 nginx 日志末尾 20MB。status 里的累计 2xx 可能比 apply 窗口多，切 100% 前要按窗口再确认一次，不够就等，不要改守护阈值。
