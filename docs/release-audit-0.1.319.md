## 优化依据与范围

- 318 CPU采样中 `NormalizeLenientJSONRequestBody` 约占3.6%，其逐字节引号和转义状态跟踪对普通紧凑JSON没有修复收益。
- 在BOM处理和大小限制之后，用标准库 `bytes.ContainsAny` 检查原始控制字节；没有控制字节时直接返回原body，保留调用方的严格JSON校验。
- 有控制字节仍使用既有修复状态机。未修改协议转换、流式、缓存解析、计费、选号、用户限制、数据库迁移。
- 新回归逐项覆盖0x00至0x1f和0x7f，确认修复后的正文与cache_control均保留；原有BOM、损坏结构、控制字节位置和扩张上限测试继续执行。
- 本机基准各两轮，256B约366ns降至170ns；1MiB约1.06ms降至0.359ms；32MiB约34.3ms降至11.0ms；均0次分配。约3倍仅指该函数，不代表整站提速3倍。
- 已通过httputil全包与httputil/apicompat竞态检查；后续Linux CI、发布制品与灰度证据在完成后补充。

## 发布门槛与经验

- 319使用独立端口与最后加载的override环境，迁移模式为validate；不复用或覆盖正在运行的318二进制。
- 318作为唯一目标回退版本。新版本先1%流量，再根据真实请求、错误率、内存余量逐步增加；物理旧机40%、新机60%。
- 必须同时验证下游正文分段到达、正常结束、缓存usage与同一笔账单；HTTP200或首个SSE事件都不能单独证明成功。
- 每阶段备份配置，先检查实际配置仍符合上一阶段，再原子替换、nginx检查和平滑reload；公网健康异常立即回退，应用进程不停止。
- 全量后至少连续监控5分钟。只保留最近旧版本时，先移除更早版本的所有备用引用并确认没有入站连接，再归档退出。
- 旧的记忆和发布守护绑定历史版本、PID、端口，不能直接重跑。当前进程、真实配置与公网返回优先于历史记录。
- 短时RSS回落或小比例灰度不能证明长期内存泄漏根治，存活请求体仍是主要堆占用。
