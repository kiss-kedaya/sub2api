# v2.1.26

修复 `Duplicate 'call_id'` 仍会透传到上游的问题。

## 背景

上游（DeepSeek 及其兼容中转）收到同一个 `call_id` 的两个 tool call 时，会整条请求 400：

```json
{"error":{"message":"Duplicate 'call_id': call_00_xxx","type":"invalid_request_error"}}
```

网关原本已有一套去重逻辑（`DedupeResponsesCallIDs` / `DedupeChatToolCallIDs`），能正确处理顶层、嵌套 `message.content`、只有 `id` 没有 `call_id`、output 重复等形态。问题出在**触发条件**：

```go
if deepSeekCallIDScope(platform, model) || strings.Contains(base, "deepseek")
```

只要分组平台不是 `deepseek`、请求模型名不含 `deepseek`、base URL 也不含 `deepseek`，去重就整个跳过。而聚合型 / 中转型上游完全可以是「中性 base URL + 中性模型别名 + 背后就是 DeepSeek」，这种情况下重复的 `call_id` 会原样送达，被上游拒绝。

## 改动

- `deepSeekDuplicateCallIDRewrite` 与 `RewriteInboundDeepSeekCallIDs` 的判断改为：平台/模型/base URL 命中 **或** 请求体里确实带 tool call（`"call_id"` / `"tool_calls"`）。去重本身是幂等的——没有重复时是 no-op，不会改动、重排或凭空生成内容。
- 新增 `bodyHasToolCallIDs`，用 `bytes.Contains` 先做廉价预判，无 tool call 的请求开销不变。
- 调整 `TestNormalizeDeepSeekResponsesRequestBodyDropsDuplicateCallID` 里关于 Kimi 的断言：原先断言「Kimi 重复 call_id 保持原样」，现在改为去重后剩一条。任何严格上游都会拒绝重复 call_id，这里没有理由保留重复。

## 测试

- `TestRewriteInboundDeepSeekCallIDs_NeutralScopeStillDedupes`：中性平台 + 中性别名 + 重复 call_id → 被清成 1 个 call + 1 个 output，且 `id` 被拆开不再等于 `call_id`。
- `TestRewriteInboundDeepSeekCallIDs_NoToolCallsUntouched`：无 tool call 的请求字节级不变。
- `TestDedupeResponsesCallIDs_ArtexShape`：复刻报错现场的形态。

无新增数据库迁移。
