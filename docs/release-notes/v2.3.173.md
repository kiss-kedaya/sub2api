# v2.3.173

本次是「独立审计跟进」版本：两轮独立审计（数据聚合路径、登录与二次验证）发现的问题在这一版收口。用量页的小时汇总补上「迟到行」自愈，渠道监控的历史数据补上稳态清理；管理端重置用户 2FA 后，被重置用户已签发的访问令牌立刻失效；登录首步「伪装二次验证挑战」开关（默认关闭）补上限速桶不相通的缺口。**没有数据库迁移，没有计费口径变化，没有前端改动。**

## 亮点

- **用量页小时汇总每小时自愈一次，补上迟到的用量行**（#670）：用量页和管理端的统计读小时汇总表。聚合任务每分钟只重算最近两分钟所在的小时，所以「创建时间落在某个小时末尾、提交又晚于约两分钟」的用量行，在原始表里有、在汇总里没有，页面上会一直少算，直到下次进程重启重算最近两天。常规写入路径最坏延迟约 40 秒，不受影响；真实的迟到来源是 Live 通话（用通话开始时间做创建时间、结束才落库，最长约 1 小时，费用为 0，只影响请求数）和媒体 / Grok 视频结算失败后的重试（带真实金额，只在重试时出现）。本版每小时对最近 3 小时再聚合一次：与每分钟的聚合共用同一条 upsert 语句、同一个互斥和 leader 锁，**不删除任何行、不改水位**（评审时特意没有复用「删后重建」的重算接口，那个接口会先删掉当天的日活用户表，把当天日活压成窗口内的人数）；按小时分 4 批，每批一个有界语句。成本：每小时约 120 万行的聚合，只在 leader 上、持有互斥期间运行（本机估算约 40 秒，**生产耗时未经验证**）。迟到超过 3 小时的行仍要靠进程启动时的重算（最近 2 天）补。
- **渠道监控历史数据在稳态下按保留期清理**（#670）：监控的 1 分钟事实表、5 分钟 / 1 小时 / 12 小时 / 1 天汇总表有保留期（1 分钟事实表 7 天，其中用户维度 3 天；汇总 7 / 30 / 45 / 90 天），但清理只在首次种子和历史回填时跑，之后每分钟只刷新实时窗口、不清理。生产实测：1 分钟事实表已留到约 11 天、错误事实表约 24 天、汇总表约 104 天，每多留一天约多 1.5GB 数据和索引。本版补上有界、分批的清理：每 30 分钟一次，由持有 leader 锁的那一轮在实时窗口刷新之后执行；每次最多 100 批、每批最多 2 万行、总时长不超过 60 秒、每条语句不超过 20 秒，批与批之间让出 150 毫秒；某张表失败只丢这张表这一轮；数据库忙（实时窗口刷新很慢）时让路；历史回填没走完时不清理。积压预计 1.5～2.5 小时分几轮清完（**估算，未经生产验证**）；清理期间监控表会产生死元组，自动清理任务会忙一阵，属预期。
- **管理端「重置用户 2FA」后，被重置用户已签发的访问令牌立刻失效**（#669）：上一版的重置只清掉刷新令牌、二次验证授权和尝试预算，已签发的访问令牌是无状态的，默认还能用到过期（默认 60 分钟）。现在重置会同时记下「撤销时间点」，此前签发的访问令牌全部作废（用户端与管理端都认）。**效果：被重置的用户在所有设备上立刻掉线、需要重新登录。** 撤销这一步失败仍只会写进返回体的 `incomplete_steps` 和审计，请求不会变成 500，返回体字段不增不改。服务器上的命令行 `-reset-admin-2fa` 共用同一套清理，一并生效，输出文案随之变化（不再说「已签发的访问令牌仍有效」）。
- **二次验证「新鲜度」遇到异常 TTL 改为拒绝**（#669）：新鲜度按授权剩余时间反推，剩余时间超过窗口总长（遗留键、改小 TTL 常量之前留下的键）时以前会算出负的年龄、被当成「刚签发」放行；现在一律视为不新鲜，按没有授权处理。只影响要求新鲜度的路由（目前只有重置他人 2FA）。
- **登录首步「伪装二次验证挑战」开关的两处修复（开关仍默认关闭）**（#669）：
  - 限速桶不相通：伪装挑战与真实挑战的限速桶以前互不相通，攻击者先把伪装桶打满，再试候选密码，错密码返回 429、对密码返回 401，仍能确认「密码正确」。现在伪装会话镜像真实账号时，与真实会话共用「账号 + 客户端 IP」桶；首步的凭证校验桶同理；不存在的邮箱与存在的邮箱（错密码）在预算耗尽后表现一致。没有让伪装会话去消耗真实账号按用户 ID 计的桶，否则任何人不需要密码，每分钟 5 个请求就能把任意已知邮箱（含管理员）的登录第二步锁死。
  - 读取最大用户 ID 失败时的拒绝服务面：读失败以前不缓存、还持锁串行，6 个并发要约 3 秒；现在失败结果缓存 10 秒（沿用上一次成功值），查询放在锁外并合并并发。
  - **开关关闭时登录行为与改动前逐字节一致**：150 个场景（未知邮箱 / 仅 TOTP / 绑 Passkey / 两者 / 无 2FA / 被禁用账号 / 大小写 × 密码对错 × 带不带假凭证 Cookie，及各种畸形请求）的黄金快照取自上一轮审计前的代码，新代码逐字节一致；另有用例钉住「关闭时真实路径不多消耗任何限速桶」。关闭时唯一的运行期差别是真实会话的第二步和 Passkey 完成多一次开关读取（进程内缓存 30 秒）。

## 变更清单

### 新增

- 仪表盘小时汇总的每小时自愈任务（#670）
- 渠道监控 v2 稳态保留期清理任务（#670）

### 优化

- 登录首步伪装与真实会话共用限速桶、读取最大用户 ID 失败时缓存并合并查询（开关默认关闭）（#669）

### 修复

- 迟到的用量行永久不进小时汇总（#670）
- 渠道监控历史数据稳态不清理保留期（#670）
- 重置 2FA 后已签发的访问令牌仍可用到过期（#669）
- 二次验证新鲜度对异常 TTL 放行（#669）

## 升级与兼容说明

- **数据库迁移**：无。可直接从 2.3.172 蓝绿替换，旧二进制可回退。
- **行为变化（有意的）**：
  - 管理端重置某用户 2FA 后，该用户在所有设备上立刻掉线（2.3.170 的说明里「已签发的访问令牌到期前仍可短暂使用」不再成立）。
  - 服务器上命令行 `-reset-admin-2fa` 的成功 / 警告输出文案变了；依赖旧文案做判断的运维脚本需要同步。
  - 渠道监控超过保留期的历史数据会在上线后几个小时里被逐步删除（这些数据本来就该没了）。
  - 上线后每小时有一次约 40 秒（估算）的最近 3 小时汇总重算，期间每分钟的聚合让路。
- **已知限制**：
  - 登录伪装开关打开后，换 IP 的探测仍有信号：攻击者在一个 IP 上用候选密码做满 5 次真实尝试烧掉真实账号的账号桶，再换一个 IP 探测，真实会话返回 429、伪装会话返回 401。要堵死只能让伪装会话也去烧账号桶，等于放开「无需密码锁人」，所以没有这样做。真实用户自己连续输错 5 次动态码的那 60 秒里，别的 IP 用正确密码探测也会看到 429；与攻击者共用出口 IP 的真实用户，在攻击者持续打满该 IP 桶期间，第二步会被 429（最长 60 秒，攻击者持续才持续）。
  - 开关打开后，首步带有效 5 分钟凭证的真实用户输错密码时，凭证会被续签而不是被清掉（不放行任何登录，伪装会话仍永远过不了第二步）。
  - 「镜像分支暴露真实凭据 ID / transports / 用户 ID」的设计（需要生产分布数据校准）、「禁用用户可被重置」与处理器注释不符，均未在本版处理。
  - 迟到超过 3 小时的用量行，仍要靠进程启动时的重算（最近 2 天）补；半小时时区和夏令时回拨小时下的汇总切分未处理（生产时区没有这两种情况）。
- **登录伪装开关**：打开前请先在真实账号上逐项验证登录流程（未绑 2FA / 只绑 TOTP / 绑 Passkey 的账号、密码对与错、不存在的邮箱），并且要等旧实例全部退出，或至少等 30 秒（开关有进程内缓存，各实例看到开关翻转的时间不同）。本版发版本身不会改变开关。
- **页面刷新**：本版没有前端改动。
- **crypto 侧车**：本版没有改动扫链代码，侧车保持 2.3.155 即可，不必更换。
