- 修复「P95 / P99 延迟过高」两条告警规则**永远不会触发**的问题：这两条规则在数据库里一直是启用状态且勾了邮件通知，但后端 `computeRuleMetric` 里**从来没有对应的指标分支**，任何一次评估都会落入兜底返回「指标不可用」；前端的可选指标列表里同样没有这两个值（而中英文文案却存在，说明是某轮清理前端时漏掉了后端那一半）。现在延迟分位数改为对用量表做**精确分位数**计算——现有的延迟直方图无法承担这件事，它最大一档是无上界的 `2000ms+`，根本回答不了「p99 有没有超过 3000ms」这个规则本身要问的问题。查询沿用仪表盘同一套时间范围过滤，并把窗口封顶 6 小时：分位数需要对窗口内的行排序，而用量表已超过 80 GB，告警评估器整体只有 45 秒预算。
- 新增**首字延迟**分位数指标（`p95_first_token_ms` / `p99_first_token_ms`）。这是上线前先量了生产数据才定下来的：请求总时长的 p50 是 12.5 秒、p95 是 114 秒、p99 是 226 秒，因为它统计的是**整段流式响应**的时间，主要取决于模型生成长度——原来的 2000/3000 毫秒阈值放上去会永久触发、变成告警风暴。首字延迟（发出请求到收到第一个 token）才是用户真正感知的「网关快不快」的指标。非流式请求没有首字延迟，因此单独统计样本数，窗口内一个首字样本都没有时该指标报「不可用」而不是 0 毫秒。
- 修复部署一致性检查在**正常重启窗口内误报**的问题：服务重启的那几秒没有进程在监听主端口，脚本无法解析正在运行的二进制，于是判定为「版本不一致」并发出 P0 告警——每次发版或重启都会复现一次。现在脚本会先看主线单元状态：没有监听且单元并非 active 时视为重启空窗，写入正常状态并说明原因（服务存活本来就有成功率/错误率规则负责，不重复告警）；只有「单元自称 active 却没有任何进程在监听」才判定为真正的故障。
