# 2.3.148-bsc6

> 热修版：只改充值扫链（`backend/internal/cryptopay`）。基于 `v2.3.148-bsc5` 再加四个提交，无数据库迁移、无其它改动。
> 只用于 crypto 扫描侧车（`CRYPTO_INSTANCE_ENABLED=true` 的那一个实例）；网关实例不需要换。

## 背景：bsc5 之后的独立复审

bsc5 上线后（2026-11-24 06:06 CST）Polygon 游标 2 分钟内从停了三小时的 97834947 前进，约 4 分钟后追平链头；BSC / ETH 持续前进；守卫独立锁 60 次采样 0 次被占。随后的独立复审（读代码 + 跑 `-race`）在 bsc4 起就存在的路由与暂停逻辑里又找到两个会让一条链再次长时间停住的缺陷，本版修掉。

## 修复

1. **宽查询被卡在「有能力的节点都在冷却」**（`rpc/pool.go`）：学到了节点 A 只收 ≤100 块、节点 B（唯一收得下 1000 块的）因限流 / 额度用尽在冷却时，宽查询原先会「无视冷却」去问 B，拿回 B 的硬错误（429 / 403），这不是 scanner 能拆分的错误，于是区间不前进，而且每次探测都让 B 继续被限流、让额度冷却形同虚设。现在这种情况直接返回「区间过宽」的可拆分错误（附带健康节点的上限作为提示），scanner 把区间对半拆成健康节点收得下的小段；冷却结束后宽查询自动回到有能力的节点。整个池都在冷却时仍然会去探测有能力的节点（行为不变）。
2. **head 阶段失败不再续期前向暂停**（`scanner/worker.go`）：前向扫描连续停滞会按 5s → 60s 退避暂停，但 head 查询本身每轮都跑。免费节点大约每分钟会有一次 head 调用被限流，原先每次都被算作一次「停滞」并把暂停整段顺延，暂停永远过不了期，前向扫描饿死（线上日志里 `forward scan paused after 70 consecutive stalled passes`）。现在 head 失败对暂停是中性的：不延长、不清除，暂停按原计划到期；真正的前向停滞仍照常累计。
3. **空闲守卫每条链有自己的时间片**（`security.go`）：一个 tick 总预算 15 秒；原先一条卡住的链会用光整个 tick，后面的健康链在已过期的 context 上跑并被误记为失败。现在每条链最多 10 秒，卡住的链按自己的超时退避；tick 自己的预算用完后，结果不记到某条链头上，没轮到的链留到下个 tick。
4. **原生币流出轮询不再受日志扫描退避影响**（`security.go`）：bsc5 把它只喂给「到期」的链，而它的间隔已被先消耗，故障链的原生转出检测可能被推迟几分钟到几十分钟。改回对全部空闲链轮询（它按自己的间隔运行，读的是浏览器地址 API）。
5. 删除无人调用的 `cursorAdvanced`（`unused` lint）。

## 验证

- `go test ./internal/cryptopay/... -race` 全部通过；新增用例逐条做了变异验证（把修复改回去，对应测试必须变红，共 7 个变异全部被杀）。
- 真实 Polygon 节点（同一批 200 个地址、976 块、8 个区间）：bsc4 与 bsc5 在无并发压力下都能 8/8 完成；线上差异来自守卫锁争用与暂停逻辑，所以验证以锁占空比和游标为准。
- 上线后盯盘：切换后 BSC 与 ETH 游标 150 秒内必须都前进，否则自动回滚到 bsc5；之后观察 Polygon 游标跟随链头、`forward scan paused` 日志不再持续出现。

## 升级与回滚

- 数据库迁移：无。
- 升级：只换扫描侧车的二进制（一次只动这一个 unit）；网关实例不用动。
- 回滚：把侧车单元指回 `/opt/sub2api/candidates/2.3.148-bsc5/sub2api` 后重启该 unit（秒级，不影响用户请求）。
- 已知小项：后台保存配置触发 reload 时，旧 worker 收尾的那几秒内，守卫会把被重载的链当空闲链多扫一次（只读；游标命名空间独立，不影响入账）；链 ID 探测成功会顺带清掉该节点的额度冷却（失败缓存 10 秒），影响很小，留待下版。
