- 计费看门狗的「零扣费请求」与「负余额用户」两条规则改为**增量告警**。它们原先用绝对值为阈值（`> 0`），而这两个状态在生产上是**长期成立**的——负余额用户 1101 人（人均仅 −$2.24，属慢性透支）、另有未定价的模型持续产生零扣费请求（约 600 次/小时）。配上 30 分钟冷却，结果是**大约每小时发出两封 P0 邮件**：这不是发现了异常，而是把已知的长期状态反复播报，只会让人忽略告警。现在改为：零扣费请求按「本窗相对上一个等长窗口的增量」判定（稳态下接近 0），负余额用户按「相对基线的增量」判定（基线存 Redis、每小时自动重置，因此它回答的是「最近一小时新增了多少」），稳态的缓慢累积不再报警，真正的突增仍然会报。基线不可用时（例如 Redis 抖动）指标报「不可用」而**不会**拿 0 当增量——否则 1000+ 的基数会让每次抖动都误报一次。
- 另外复核了其余计费与运维规则在当前生产数据下是否会长期成立：预扣积压实测为 0、零扣费比例实测 0.65%（阈值 2%），均不会误报。
