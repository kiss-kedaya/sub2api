# v2.3.154

本次为稳定性与体验版本，共合入 25 个 PR。重点是：跨协议转换修复、身份校验补口、管理端体验、链上扫描稳定性。

## 亮点

- **跨协议转换**：修复 Anthropic 透传账号无法走 `/v1/responses` 的问题（此前会报「无可用账号」503）；转换链现在会透传请求体未知字段、入站 query 参数，并把上游错误原样回传，不擅自改写用户参数。
- **Base URL 容错**：任意数量的 `/v1` 前缀（`/v1/v1/messages`、`/v1/v1/v1/...`）以及不带版本段的裸路径都能正确路由；带前缀的路由（antigravity / codex）同样支持。
- **链上扫描稳定性**：修复分片签名器锁定时扫描游标被冻结的问题（BSC 长时间 0 块/分的根因）；修复后台扫描锁等待不透明的问题。
- **身份校验补齐**：创建/轮换 Key、变更 Key 明文、二次查看密钥，全部要求三选一身份校验（密码 / TOTP / Passkey），并堵上批量轮换、更新、幂等重放三个绕过口。
- **双因子策略**：绑定 Passkey 的账号登录与敏感操作按因子组合校验，两个都绑定则两者都要过，统一 5 分钟窗口。
- **管理端**：使用记录筛选区重做（常用项 + 高级筛选折叠 + 操作条主次）；同步模型等只读操作不再要求二次验证；验证弹窗补齐确认按钮。
- **监控**：缓存率低于 30% 的渠道状态条判为黑色（视为不可用）；5xx 告警拆分上游透传与网关自产，避免上游抖动误报。

## 升级与兼容说明

- **数据库迁移**：本次含 3 个待执行迁移（`337_api_key_secret_auth_factor`、`337_ops_error_5xx_split`（已执行过的文件已改名保留原内容）、`338_ops_error_logs_5xx_time_index_notx`、`339_ops_error_5xx_rule_reconcile`）。`338` 是 `CONCURRENTLY` 建索引，不锁表，但会占用 IO；`339` 会**禁用**描述未带标记的 `gateway_5xx` 存量告警规则并在描述中标注原因。
- **上线后需人工确认**：`gateway_5xx` 规则被 339 禁用后，需在后台按新口径（仅统计网关自产 5xx）重设阈值并重新启用，否则网关 5xx 告警处于关闭状态。原阈值数值未被修改。
- **创建 Key 需身份校验**：账号存在可用因子时，创建 / 批量轮换 / 有明文回执的更新都需要携带校验材料；旧前端调用会被拒绝（返回 `VERIFY_REQUIRED`）。
- **查看密钥需授权**：`GET secret-seal` 需要 5 分钟一次性的 `X-Reveal-Grant`，且验证因子需与封存时一致。
- **step-up 凭证 Redis key 格式变更**：滚动窗口内 5 分钟免重复凭证会失效，可能多弹一次验证码，不影响授权结果。
- **错误码变化**：协议不匹配由 503 改为 400 `PROTOCOL_MISMATCH`；模型不支持改为 404 `MODEL_NOT_AVAILABLE` 并附可用模型列表。客户端应按 code 分支处理。
- **两处路径语义扩展**：`/backend-api/codex` 前缀允许任意版本段；`/antigravity` 前缀在唯一命中时补版本段（保守策略，多命中不猜）。

## 部署

1. 从 Release 下载 `sub2api_2.3.154_linux_amd64.tar.gz` 与 `checksums.txt`，先 `sha256sum -c checksums.txt`。
2. 新二进制执行 `-check-migrations` 确认待执行迁移清单，再 `-migrate-only`（建议低峰，`338` 建索引会占 IO）。
3. 蓝绿部署：新端口启动新实例，`/health` 与首页 200 后先接 1% 流量，观察错误率与日志再逐步放量。
4. 旧实例保留至新版本稳定，回滚只需把流量切回上一版端口。
5. crypto 侧车（`sub2api-crypto-api-*`）建议与主实例同批更新，BSC 游标卡死依赖本版修复。
