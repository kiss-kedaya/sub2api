# v2.3.168

本次是「降 CPU、降内存」的性能版本：网关请求预处理、DeepSeek 请求改写、响应侧逐行观察器几处热路径改成线性 / 零拷贝，并修掉一处会让整份请求体在内存里多活一段时间的子串泄漏。**没有数据库迁移，没有接口和计费口径变化**；所有改动都用旧实现当对照做过逐字节 / 逐值对拍，写给客户端的响应字节与以前一致。

## 亮点

- **DeepSeek 请求改写由「二次方」改为「线性」**（#648）：补占位 reasoning、补齐 thinking 回放、工具调用配对、托管搜索改写等路径，以前对每条历史消息各调用一次 `sjson.Set`，每次都整体复制请求体并从头定位路径，成本是「消息数 × 请求体大小」。现在一遍扫描收集补丁、一次分配输出。300 条消息 / 约 800KB 的合成体上：补占位 reasoning 61.6 ms → 0.86 ms（71 倍），分配 160 MB → 0.67 MB；补齐 thinking 回放 41.7 ms → 1.0 ms；工具输出补全分配 987 KB → 39 KB。JSON 不合法或形状不对时返回原请求体，行为不变。
- **请求体预处理先用原文探针判断「无需改写」，跳过整包 JSON 解码**（#649，若本版未包含则见下一版）：绝大多数请求根本不需要被改写，却每个请求都把整个请求体解成 `map[string]any` 或整份 `json.Valid`。现在先在原文上证明「不会变」，证明不了就走原来的整包解码。
- **响应侧逐行观察器提速**（#652）：连接追踪 / 自动化观察 / 请求模型回写 / 静默拒答检测等逐行观察器，在行里没有关心的字面量时直接跳过整行解码。OutcomeObserver 3～4 倍、自动化观察器 6～8 倍、模型回写 3～36 倍（每块都要真改写的 Chat 流持平）；原生 Chat 流端到端 1000 事件 4.83 → 2.80 ms，大请求 6.49 → 2.76 ms。写给客户端的字节与以前逐字节一致。
- **修复请求体在内存里多活的子串泄漏**（#646）：客户端函数工具名集合的 map key 是整份请求体拷贝的子串，导致整份拷贝一直活到请求结束；改成克隆。2 MB 请求体上该函数分配 2.1 MB → 288 B；`input` 条目 id 清洗、Grok 兼容字段剥离改为一遍扫描一次输出（256 条 8 KB 条目：9.4 MB / 1291 次分配 → 2.1 MB / 13 次）。

## 变更清单

### 优化

- DeepSeek 请求改写单遍补丁（#648）
- 请求体预处理探针与 `validJSON`（#649）
- 响应侧逐行观察器前置判断，跳过无关行的整行解码（#652）
- 工具名 map 键克隆、`input` id 清洗与 Grok 字段剥离一遍扫描（#646）

## 升级与兼容说明

- **数据库迁移**：无。可直接从 2.3.167 蓝绿替换，旧二进制可回退。
- **行为**：JSON 带缩进或键序特殊的少数 DeepSeek 请求，改写后的数组元素间空白可能与旧实现不同，解析后的值逐值相等；紧凑 JSON 与旧实现逐字节一致。
- **页面刷新**：本版前端文件没有变化。
- **crypto 侧车**：本版没有改动扫链代码，侧车保持 2.3.155 即可，不必更换。
