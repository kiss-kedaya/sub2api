# v2.1.28

停止 DeepSeek 响应改写（改为可选开关），并修复 chat 响应 message.role 为空的问题。

## 背景：用官方 API 实测出的差异

拿官方 https://api.deepseek.com 与线上网关逐项对比后确认：官方 DeepSeek 现在原生支持 /v1/responses，返回结构化 reasoning：

    {"type":"reasoning","content":[{"type":"reasoning_text","text":"..."}],
     "encrypted_content":"a86c2c20-..."}
    {"type":"function_call","id":"4e5f2924-...","call_id":"call_00_ET_..."}

id 是 UUID、call_id 是 call_00_...，两者本来就不同，不需要我们再用 fc_ 前缀去拆分。

## 改动

### 1. DeepSeek 响应改写默认关闭

新增 gateway.deepseek_response_compat_enabled（默认 false）。

关闭后不再执行：

- DSML 内联工具调用解析（rewriteDeepSeekResponseBody）
- reasoning 重组、call_id 重建（sanitizeResponsesCallIDs）
- 搜索工具注入与网关代执行（injectDeepSeekSearchTool / applyDeepSeekSearchResults）

这些改写会把上游已经正确的响应再加工一遍，实测导致 reasoning item 整段丢失、Responses 顶层字段被剥掉。只有接入不支持原生工具调用的老式 DeepSeek 兼容中转时才需要打开。

### 2. rewriteDeepSeekResponseBody 不再无条件重写 call_id

原文在 body 里既没 DSML 也没 think 标签时，仍会调用 sanitizeResponsesCallIDs 重写所有 call_id。现在直接原样返回，保住上游的 id/call_id 结构。

### 3. 修复 chat 响应 message.role 为空

实测我们网关给客户端返回 role 是空字符串，官方与正常中转返回的是 assistant。严格客户端会拒绝空 role。

新增 repairChatCompletionMessageRole / repairChatCompletionChunkRole：

- 非流式：choices[].message.role 为空时补 assistant
- 流式：只修补没有任何其它载荷的开启 delta，内容/工具 delta 一律不动
- 已有正确 role 的响应字节级不变

## 上游横向对比（实测）

    | 指标                  | 官方      | hongai(#29159) | lcodex(#33666) | 我们        |
    | chat role             | assistant | assistant      | 空串           | 空串 -> 已修 |
    | Responses reasoning   | 有        | 无             | 无             | 无          |
    | function_call.id      | UUID      | item_          | item_          | item_       |

lcodex.cc 与 hongai.co 都是 sub2api 系网关；role 为空是同类实现的通病，本次在源头修掉。

reasoning item 缺失是 chat 转 Responses 的固有限制（chat 协议没有 reasoning item 结构），不是本次改动的回归。要拿到 reasoning，需要用 api_protocol=responses 的账号。
