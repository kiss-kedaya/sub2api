# 2.3.148-bsc5

> 热修版：只改充值扫链（`backend/internal/cryptopay`）。基于 `v2.3.148-bsc4` 再加三个提交，无数据库迁移、无其它改动。
> 只用于 crypto 扫描侧车（`CRYPTO_INSTANCE_ENABLED=true` 的那一个实例）；网关实例不需要换。

## 修复：Polygon 在 bsc4 之后仍然停住（游标停在 97834947，03:17 CST 起）

**现象**：bsc4 已让 BSC / ETH 游标持续前进，Polygon 仍停住，用户在 Polygon 上的充值要等很久才入账。

**根因**（线上锁占用采样 + 真实节点复现 + 独立审查）：
1. 全局扫描 advisory lock 被「空闲链钱包守卫扫描」长期占用（采样占空比约 96%）。守卫扫的是没开充值扫描的链；其中一条 plasma 的三个免费节点从 11 月 8 日起一直 403 / 429，每 5 秒整轮失败一次、占着同一把锁、打约 150 个请求。定时入账扫描只能偶尔抢到锁。
2. 一个区间只有它的每个 200 地址批次的 `eth_getLogs` 都成功才算完成（游标才前进）。Polygon 有十几个批次，免费节点对一批同时到达的请求只要拒绝其中一个（429），整个区间作废，下一个 pass 把所有批次再并发打一遍，同样的突发再被拒绝。

**改动**：
- 空闲链守卫改用自己的 advisory lock（`GuardScanLockKey`），永远不再占用充值扫描的锁；充值扫描锁键不变，新旧版本并存时充值仍互斥。
- 守卫的失败退避逐链各自计算（5s 起翻倍、上限 5 分钟、±20% 抖动，第一次成功立即清零）：一条死链（plasma）不再拖慢其它健康空闲链的未授权流出检测；别的实例占着守卫锁（`ErrScanBusy`）不算失败。
- 一个区间里失败的地址批次，在同一次扫描内只重跑失败的批次：最多 3 轮，每轮先等 0.5s / 1s / 2s（抖动），每轮并发减半。只有「本区间至少有一个批次成功回答过」才重试（全部失败说明节点宕机或额度用尽，不在扫描锁内空等）；额度耗尽、区间过宽、响应非法、取消都不重试。重试后区间仍必须所有批次成功才算完成，游标语义不变。

## 验证

- `go test ./internal/cryptopay/... -race`（rpc / scanner / 根包）通过；新增用例都做过变异验证（见 PR）。
- 上线后盯盘：守卫锁占空比（采样 40 秒）明显下降，Polygon / BSC / ETH 游标 `last_block` 持续前进；切换后 BSC 与 ETH 游标 150 秒内必须都前进，否则自动回滚到 bsc4。

## 升级与回滚

- 数据库迁移：无。
- 升级：只换扫描侧车的二进制（一次只动这一个 unit）；网关实例不用动。
- 回滚：把侧车单元指回 `/opt/sub2api/candidates/2.3.148-bsc4/sub2api` 后重启该 unit（秒级，不影响用户请求）。
- 已知小项：后台保存配置触发 reload 时，旧 worker 收尾的那几秒内，守卫会把被重载的链当空闲链多扫一次（读取，不写入账；游标命名空间独立，不影响入账）。
