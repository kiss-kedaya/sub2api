# v2.3.172

本次是「降库压力 + 降 Redis 内存」版本：按 API Key 的用量报表不再每隔几分钟就把重 Key 的 15 天用量表整段重扫一遍，也不再有一批被超时砍掉、白白读盘的扫描；DeepSeek 原生推理内容在 Redis 里改成压缩存储。**没有数据库迁移，没有计费口径变化，没有前端改动。**

## 亮点

- **按 Key 的用量聚合进一步降低库压力**（#667）：`GET /v1/usage`（CC Switch 等客户端轮询）、Key 用量页等按 Key 的多日聚合，是生产库上占比最大的一类重查询：生产实测里，按 Key 的「按模型」和「按日趋势」聚合占慢语句总时间的约八成。它们的特点是「很多个不同的重 Key 各自每几分钟重算一次」，一个重 Key 的 15 天用量聚合要随机读大量堆页，在库盘满载时要 16～28 秒；而之前的加载预算是 15 秒，超时就被砍、不写缓存、记忆 30 秒后又重来——同一个 Key 一遍遍白读盘却什么也没产出。本版：
  - 没带 `start_date` / `end_date` 的默认 30 天窗口，网格从 5 分钟放宽到 **15 分钟**，并且**每个 Key 的网格有自己的相位**（由 Key 的 ID 稳定算出，两台网关一致），避免所有 Key 在同一时刻一起重算；
  - 按 Key 的多日聚合缓存从 5 分钟放宽到 **15 分钟**（单日窗口、「今日 / 累计」看板、用户页、管理端报表等其它聚合保持原有的 60 秒不变）；
  - 这一类聚合的加载预算从 15 秒放宽到 **28 秒**（小于库角色 30 秒的 statement_timeout，这样结束扫描的是应用自己的预算），仍然跑不完的，超时记忆从 30 秒放宽到 **5 分钟**；其它聚合保持 15 秒 / 30 秒不变，交互行为不变；
  - 并发闸本身不改。评估见 PR：排队的最长等待不变，稳态占槽时间下降，唯一变坏的是冷启动 / 午夜换窗口的瞬间，每一轮槽被占满的窗口最多多约 13 秒。
  - 预期（**未经生产验证，上线后复测**）：重 Key 的重算频率降到约 1/3，被应用超时取消的无效扫描接近 0。
- **DeepSeek 原生推理内容在 Redis 里改成压缩存储**（#666）：生产 Redis 的数据里，`reasoning_content:deepseek-native-v1:*` 这一族占了约 99% 的字节（均值约 6.7KB、TTL 7 天），是纯文本。现在写入时对这一族的较大值做 gzip 压缩（真实 LLM 思考文本实测约 2.3～2.6 倍，合成基准 6.8KB 约 2.1 倍；写入每次约 125 µs、读取解压约 32 µs，写入量只有每秒几次），读取按 gzip 头自动识别，压缩前写入的明文照常读出，对调用方完全透明。key 名、7 天 TTL、所有调用方行为都不变。**效果是渐进的**：已经写入的明文键要等 7 天自然过期，只有新写入的才压缩，所以内存和 AOF 体积是一周内逐步下降到约 4 成～5 成，不是上线即降。
  - 只压缩 DeepSeek 原生这一族；另一个很小的老族（Responses→Chat 桥接用）保持明文，因为旧版本读到压缩字节会把乱码当历史推理发给上游。
  - 任何读不出来（压缩流损坏 / 被截断 / 解压超过 4MiB 上限）都按「未命中」处理，调用方对未命中本来就是降级（补占位符），不会多出一类错误。

## 变更清单

### 优化

- 按 Key 的多日聚合：默认窗口 15 分钟网格 + 按 Key 相位；缓存 15 分钟；加载预算 28 秒、超时记忆 5 分钟（#667）
- DeepSeek 原生推理缓存值透明 gzip 压缩（#666）

## 升级与兼容说明

- **数据库迁移**：无。可直接从 2.3.171 蓝绿替换，旧二进制可回退。
- **行为变化（有意的）**：
  - `GET /v1/usage` 的「按模型」`model_stats` 与「按日趋势」`daily_usage` 最多滞后 **15 分钟**（2.3.171 是 5 分钟）；同样放宽到 15 分钟的还有：`/v1/sub2api/usage` 的 `last_7_days` / `this_month` / `daily`、Key 用量页的区间汇总与按日明细、管理后台按 `api_key_id` 过滤的趋势 / 模型分布（窗口超过一个自然日时）。它们的「今日」块、单日窗口、「今日 / 累计」看板仍是最多滞后 60 秒。
  - 重 Key 的报表现在最多要等 28 秒才可能出现：`/v1/usage` 自己仍只等 2 秒，超过就先返回不带报表的核心响应，加载在后台继续并写缓存，之后的轮询命中缓存；Key 用量页这类同步等待的入口最多等 28 秒（之前是 15 秒后报错）。
- **已知限制**：
  - 单次扫描仍超过 28 秒的 Key 还是会失败，只是改成每 5 分钟才重试一次；要从根上解决需要按 Key 维度的小时汇总（要迁移，另议）。
  - 按日趋势的窗口按用户时区午夜对齐，重算时刻由「午夜换窗口后的第一次轮询 + 缓存时长」决定，不是网格；午夜后的几小时里重 Key 的重算可能成簇（未验证）。
  - 并发闸的评估按默认配置（每进程 8 个共享槽、排队上限 8 秒、同一用户最多占 2 个槽）估算；生产没有覆盖这些默认值。
- **回退**：回退到 2.3.171 即恢复 5 分钟网格 + 5 分钟缓存 + 15 秒预算；缓存键含窗口起止，蓝绿切换期间新旧版本基本各用各的键，不会串。回退后，已写入的压缩推理缓存键在 7 天内表现为未命中（降级为占位符，不报错，与 Redis 被清空时一样），或被新一轮推理覆盖成明文，不需要任何数据迁移。
- **蓝绿期间**：新进程写入的压缩推理缓存，旧进程读到会按未命中处理（那一轮丢掉对应的历史推理，不报错）；旧进程写的明文，新进程照常读。
- **页面刷新**：本版没有前端改动。
- **crypto 侧车**：本版没有改动扫链代码，侧车保持 2.3.155 即可，不必更换。
