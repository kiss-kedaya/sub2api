# 2.3.148-bsc4

> 热修版：只改充值扫链（`backend/internal/cryptopay`）。基于 `v2.3.148-bsc1`（= v2.3.148 + BSC 分片锁游标修复 #581）再加五个提交，无数据库迁移、无其它改动。
> 只用于 crypto 扫描侧车（`CRYPTO_INSTANCE_ENABLED=true` 的那一个实例）；网关实例不需要换。
> 取代已撤回的 `bsc2` / `bsc3`（bsc3 在线上 14 分钟内让 BSC、Ethereum、Polygon 游标一起停住，已回滚，见下文「bsc3 事故」）。

## 修复：公共 RPC 额度 / 限流下充值扫链反复卡死（Polygon 十几次「卡死半天」的根因）

**现象**：某条链（Polygon、此前的 BSC / ETH）的扫描游标停住几小时，用户充值不入账，要等免费节点的日额度重置才恢复。

**根因**（线上日志 + 真实节点复现 + 独立审查）：
1. 节点池里只有少数节点能一次查约 1000 块；有的免费档只收 100 / 50 块，有的日额度或预付余额已用完（HTTP 429 / 503）。池子对每次失败的调用把所有节点轮一遍，同一个超宽查询被无能力的节点反复拒绝，真正的原因（有能力的节点被限流）还被最后一个节点的 400 盖住。
2. 端点冷却把同一批并发调用的失败按 N 次计数（5 个并发批次被同一次限流拒绝，冷却直接 48 秒）。
3. 每个扫描 pass 都派生新的节点池，健康记录和学到的区块上限随之丢失：节点刚说「日额度用完」，5 秒后又被问一遍。
4. 每个 pass（5 秒一次）对每条链的所有配置节点各发一次 `eth_chainId` 校验，答案永远不变，却照样计入提供方的日额度。
5. 失败的链照样每 5 秒重试一次，每个失败调用最多打 7 个节点，几小时烧光所有免费日额度，然后一直卡到提供方重置计数。

**改动**：
- 池记住节点自己说出的 `eth_getLogs` 区块上限（HTTP 400/413/422 或 JSON-RPC 错误文案，30 分钟过期）；宽查询只发给有能力的节点；所有节点都拒绝时返回可拆分错误，由 scanner 对半拆。失败时优先报告真实的硬错误（限流 / 宕机 / 额度），不让「范围太宽」盖住它。
- HTTP 402 / 429 / 503 且文案是日 / 月额度或预付余额用尽的节点冷却 15 分钟（只看 HTTP 状态码，交易类 JSON-RPC 错误不会被当成额度）。
- 端点冷却把同一批并发调用的失败只算一步退避。
- 派生出来的节点池继承同一份健康记录，冷却与学到的上限跨 pass 生效。
- 已证明服务某条链的节点 5 分钟内不再重复做链 ID 校验（失败只记 10 秒）。
- 节点返回的文案先截到 512 字节再分类；HTTP 错误页只保留固定短语、数字和额度标志，不留原文进日志。
- 定时扫描里，转发游标连续卡住（确认块在游标之后、游标没动，或取不到 head）的链，转发批次和 replay 按 5s → 10s → … → 60s 退避（±20% 抖动）；head 安全窗口、head 观察和覆盖记录照常每轮运行，所以卡住期间新充值仍然显示为待入账、安全扫描通过后仍可入账；被跳过的尝试作为错误上报。第一次失败不延迟，成功或游标前进立即清零；手动补扫永远不受影响。

## bsc3 事故（2026-11-24 03:17–03:31 CST）

bsc3 额外带了「未配置 `rpc_throttle_ms` 时默认每个节点两次调用起点间隔 150ms」。一个扫描阶段是 13 个地址批次，单节点上 13 次 `getLogs` 排队就是 2.4 秒（不限速时 5 毫秒，约 480 倍）；idle 钱包守卫扫描（plasma，3 个免费节点全是 403/429）每轮要打约 58 次调用，从不到 5 秒变成 8.8 秒，超过它自己的 5 秒 ticker，于是守卫扫描放锁后立刻重新拿锁，全局扫描 advisory lock 几乎 100% 被占（40 秒采样 168/168），定时入账扫描拿不到锁：BSC、Ethereum、Polygon 游标一起停住 14 分钟。回滚到 bsc1 后立即恢复。

**bsc4 已撤回该默认值**：未配置 = 不限速（与 bsc1 一致），配置项保留，新增测试固定该语义。

## 验证

- 真实 Polygon 节点（同一批 200 个地址、976 块、5 路并发批次 × 6 轮 = 30 次调用）：旧代码 59 次 HTTP 请求，新代码 40 次；blazingnode 400 从 12 次降到 3 次，drpc 从 5 降到 1，tatum 的 429 从 4 降到 0（该测量未含后两项改动带来的节省）。
- 独立审查（跑代码实测）发现的问题均已修复：暂停期间 head 阶段被一并跳过导致 pending 入账饥饿、错误日志被吞、批次级安全失败不被识别为卡住、head 失败时无声跳过 replay、JSON-RPC 超长文案的 CPU 放大、HTTP 文案进日志、健康记录每个 pass 重建。
- `go test ./internal/cryptopay/...`（含 `-race` 的 rpc / scanner 包）通过，新增用例都做过变异验证。
- 上线时自动盯盘：切换后 BSC 与 ETH 游标 150 秒内必须都前进，否则自动回滚到上一版。

## 升级与回滚

- 数据库迁移：无。
- 升级：只换扫描侧车的二进制（一次只动这一个 unit）；网关实例不用动。
- 验证：`crypto_scan_cursors` 里各链 `last_block` / `updated_at` 持续前进；日志里 429 / 额度类错误明显减少；`deposit-info` 返回体大于 70 字节。
- 回滚：把侧车单元指回 `/opt/sub2api/candidates/2.3.148-bsc1/sub2api` 后重启该 unit（秒级，不影响用户请求）。
