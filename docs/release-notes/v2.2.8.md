# v2.2.8

修 `/v1/usage` 在余额模式下恒返回 500 `Failed to get user info`。

## 症状

监控探针（`sub2api-balance-alert/1.0`、`LinkAI-UpstreamMonitor/1.0`）每 5 分钟
轮询 `GET /v1/usage`，稳定拿到：

```json
{"error":{"message":"Failed to get user info","type":"api_error"},"type":"error"}
```

线上 `ops_error_logs` 统计（近 7 天）：user 4145 + key 5304 共 228 次，
user 3704 + key 34511 共 97 次，各自只有一个固定 IP，全部来自这两个 UA。

## 根因

`Usage()` 的顺序是：先跑三个按 API Key 的统计查询（`GetAPIKeyDashboardStats`、
`GetAPIKeyDailyUsage`、`GetAPIKeyModelStats`），最后才在 `usageUnrestricted`
里调 `h.userService.GetByID(ctx, subject.UserID)` 取余额。

这两个 key 的 `usage_logs` 分别有 53.4 万 / 10.9 万行，实测一次 `/v1/usage`
要 **7.1 秒**。监控探针 HTTP 超时更短，会先断开；请求 ctx 随即取消，
`GetByID` 拿着已取消的 ctx 查库，直接返回 `context canceled`，被映射成 500。

同一台机器上 `handler/usage_handler.go` 大量 `pq: canceling statement due to
user request` / `context canceled` 是同一个根因家族。

**不是**：用户被删（两个用户 `status=active`、`deleted_at` 为空）、
数据库慢（`users_pkey` 查询 0.06ms）、key 失效（同 key 的 `/v1/messages`
一直有正常流量）。

## 修法

1. 余额模式的用户查询提到统计查询**之前**，并用 `context.WithoutCancel(ctx)`
   隔离客户端断连。
2. `usageUnrestricted` 不再自己查库，改为接收调用方传入的 `*service.User`，
   只有 `nil` 才报 500，避免再被已取消的 ctx 拖下水。
3. 加回归测试 `TestUsageUnrestrictedRequiresPreloadedUser`：ctx 已取消且未
   预加载用户时必须直接 500，不得回落到查库。

## 验证

- `go build ./...`、`go vet ./internal/handler/` 通过
- `go test -tags=unit ./internal/handler/` 37s 全绿
- `go test -tags=unit ./internal/service/` 216s 全绿
- 线上实测 `/v1/usage`（大 key）：`code=200`，`time_total=7.13s`

## 未解决（单独跟踪）

统计查询本身仍要 7 秒，属于性能问题而非本 bug。需另做汇总表或缓存，
不要在 `/v1/usage` 里实时聚合几十万行。

## 回滚

回滚到 `v2.2.7`；本次无数据库迁移、无新增配置。
