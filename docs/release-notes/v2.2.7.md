# v2.2.7

补齐 v2.2.6 的流式门控缺口，并修复 CI 阻断项。

## 1. keepalive 门控在所有流式实现上都有 Arm

v2.2.6 在 `/v1/messages` 入口加了 `GateOpenAIStreamSSEKeepaliveUntilUpstream`：
上游响应头到达前心跳保持静默，避免把上游 `400/529` 固化成 `200`。但只有
Anthropic 直通路径调用了 `ArmOpenAIStreamSSEKeepalive`，其余实现拿到上游
`200 + SSE` 之后不会解锁 —— 长思考（首个可见输出前数百秒）期间不再发心跳，
中间层会按空闲超时把连接判死，回 504。

本次补齐解锁点：

| 路径 | 位置 |
|---|---|
| Anthropic 直通 | `handleStreamingResponseAnthropicAPIKeyPassthrough`（既有） |
| Anthropic OAuth/原生 | `handleStreamingResponse` |
| OpenAI 原生 Anthropic 端点 | `handleNativeAnthropicStreamingResponse` |
| Anthropic→Responses 转换 | `handleResponsesStreamingResponse` |
| Anthropic→Chat 转换 | `handleCCStreamingFromAnthropic` |
| OpenAI → Anthropic（messages） | `handleAnthropicStreamingResponse` |
| Gemini compat（非原生/原生） | `handleStreamingResponse` / `handleNativeStreamingResponse` |
| Antigravity（Claude/Gemini/Upstream） | 三处流式入口 |
| Bedrock EventStream | `handleBedrockStreamingResponse` |

`gateway_handler.go` 里 Forward 成功后的那次 `Arm` 已删除：`Forward` 是同步
阻塞的，流在返回前已经写完，那次调用没有意义（真正的解锁在 service 层）。

## 2. 门控不能绕过

`WriteOpenAIStreamSSEHeartbeat` 被门控拦下时改为返回 `handled=true` 且写出
0 字节。此前返回 `handled=false` 会让调用方退回直接写 `ResponseWriter`，
绕过门控把状态码固化成 200。

等待并发槽位的 ping 只有在真的写出字节时才标记 `streamStarted`，避免上游
`4xx/5xx` 被错误降级成流内错误帧。

## 3. failover 判定

`IsOpenAIStreamSSEKeepaliveArmed` 只认「被 gate 且已提交」的入口。未 gate 的
入口（chat-completions / responses / compact）仍按心跳字节扣除来判定能否
重放，不会被一刀切禁掉换号。
