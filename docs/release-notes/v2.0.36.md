本版聚焦「监控可信」与「Grok 兼容」：修掉一个会让渠道监控静默停摆的定时任务缺陷、两处部署看门狗的自身问题，补上 Grok 4.7 全系被丢掉的思考等级，并让主 CI 从连续三天的红色恢复。

## 修复

- **渠道监控不再静默停摆。** 实时聚合的窗口原先固定为「最近 2 分钟」，而这个窗口只覆盖相邻两次 tick 之间的那段——只要有一次 tick 没跑（抢不到集群单例锁、单次运行超过 3 分钟超时、进程重启），中间那几分钟就落到之后每一个窗口之外，**永远不会被重算**，1 分钟事实表出现空洞，前端全量显示「样本不足」。现在窗口起点取「上次成功写入的水位」，任何缺口都会在下一次成功运行后自动补齐。线上实测水位曾冻结在某一分钟长达 16 分钟、而源数据（每分钟 1400~1950 条）完全正常——问题从来不在采集。
- **修好「补历史空洞必须重启进程」的副作用。** 上一处修复依赖持久化水位，但它原先只在进程启动时读一次，于是把水位往回拨以便回填历史空洞时**必须重启服务才生效**。现在每个 tick 重新读一次（单行查询，相对每分钟一次的多表重写可忽略）。稳态下读到的值与内存镜像一致，健康时行为没有任何变化；换来的是可以不停机地修复历史空洞。
- **Grok 4.7 全系的思考等级不再被丢弃。** 判断「模型是否支持思考等级」是一张硬编码白名单，而 4.7 整个系列都不在其中，于是 `reasoning.effort` / `reasoning_effort` 会被**删除**。线上近 24 小时实测：grok-4.7 有 79,753 次请求（Grok 里量最大）、grok-4.7-build-fast 1,327 次，均在被剥掉之列；grok-4.6 才 59,997 次。现已加入 `grok-4.7`、`grok-4.7-latest`、`grok-4.7-build-fast`。**`xhigh` 档位仍只对 4.6 放行**——尚无证据表明 4.7 接受该档位，发过去可能被上游拒；4.7 客户端发 `xhigh` 会降级为 `high`。
- **部署看门狗的单元名解析。** 它用一个贪婪正则从 `systemctl status` 输出里取单元名，实测只取到 `.service` 后缀，于是状态文件里写着 `unit .service`。这不只是显示问题：**「无监听时判断是重启窗口还是真故障」那段逻辑正是靠这个单元名**，取空等于把「避免重启窗口误报 P0」的保护静默废掉。现改从 cgroup 精确取，并保留按 `MainPID` 反查的兜底。
- **部署看门狗不再在每次发版时误报。** 「运行中的二进制 ≠ EXPECTED_VERSION」是部署的**正常中间态**（先换二进制、后改期望值），而规则用的是绝对值阈值，于是每次正常发版都会报一次，且只要期望值没跟上就**一直报**。现在不一致必须**持续**超过 15 分钟才算错，且计时落盘、与检查频率无关。结构性故障（期望值文件缺失、单元自称 active 却无人监听）**不走宽限**，仍立即上报。
- **主 CI 从三天全红恢复。** 两个独立原因：一是前端作业逐个执行 `deploy/rollout/test_rollout329..336_guard.py`，而这些脚本**从未被 git 跟踪、干净检出上根本不存在**，该步骤自 09-27 起每次都以「文件不存在」失败；二是 lint 报出 5 处问题（3 处 gofmt、1 处赋值后未读取、3 处测试辅助里未检查的写入）。前者已移除该步骤——需要这些守卫回归 CI 的话，得先把脚本提交到未被忽略的目录；后者已全部修好。

## 性能

- **Grok 请求体改写少一次整份解析。** 重新编码后的 `input` 数组原先交给通用写入接口，由它再解析一遍整个请求体来定位字段；而 gjson 查找时已经给出了该字段的精确字节跨度，现在直接按跨度拼接。跨度不可信时自动退回原路径，行为不变。
- 分配棘轮测试（`TestPatchGrokResponsesBodyAllocationCeiling`）继续守住该链路的分配上限，防止再次出现「逐字段整份重写」。

## 配置变更

- 无新增必填配置。部署看门狗新增两个可选环境变量：`MISMATCH_GRACE_SECONDS`（默认 900）、`MISMATCH_SINCE_FILE`（默认 `/opt/sub2api/deploy-check.mismatch-since`）。

## 升级注意

- **数据库迁移：无。**
- 本版只改后端行为，前端产物无变化，不需要重新构建前端。
- 部署请按滚动方式进行：逐个实例换二进制并确认监听后，再切换下一个，避免同时重启造成服务空窗。
- 升级后建议核对部署看门狗状态文件：`version_mismatch` 应为 0，且 `detail` 中的单元名应显示为完整的 `<服务名>.service`——若显示为 `.service`，说明脚本仍是旧版。
