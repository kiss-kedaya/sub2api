# GPT 分组 Key 迁移记录

日期：2026-09-17，北京时间。

## 范围与结果

- 按用户要求，将 GPT Pro「BUG」（23）及 GPT 普通分组（17）的用户 Key 迁至 GPT 稳定高缓分组「禁蒸馏」（9），目标默认倍率0.07。
- 首轮3493个Key：BUG主绑定685个、普通主绑定1851个、智能路由备用引用957个。执行前的查询数量会随用户编辑变化，实际以事务前备份为准。
- 补迁执行期间新出现的旧组绑定后，合计处理3494个不同Key。最终未删除Key的主绑定与智能路由中，对17、23两组的引用均为0。
- 所有源组引用替换成9；已有9则按原先顺序去重，其他分组相对顺序保留。只剩一个分组时保留有效主绑定、清除冗余多路由行，不留下空绑定。
- 目标分组原有用户优惠倍率保持，未改组倍率、用户余额、Key额度、用量、状态、有效期、IP规则、并发或密钥内容。执行期间发生的用户改名与另选其他非源分组保留，不反向覆盖用户操作。
- 未停用或删除任何分组。今后若要禁止新建或重新绑定源组，还需将源组停用；本次没有擅自更改分组状态。

## 验证与经验

- 首次缓存刷新受到容器遗留 `REDISCLI_AUTH` 干扰，数据库迁移已提交，未再次执行全量迁移。确认Redis实际未设置密码后，使用 `env -u REDISCLI_AUTH` 清理客户端遗留变量，仅对目标Key的auth缓存执行DEL与既有失效频道PUBLISH。未改Redis服务配置，未清空全库缓存。
- 定向失效成功后再次检查全部迁移Key；密钥指纹、额度、状态等字段保持。所有保留智能路由的第一项与主分组一致，单项冗余路由为0。
- 以原有管理员测试Key请求两机和公网 `/v1/sub2api/billing`，三次均HTTP200，组倍率和实际倍率均0.07；不创建新Key、不消耗模型余额。
- 不能只迁 `api_keys.group_id`：智能路由的备用组引用也会继续选择旧组。必须一起替换并去重，再核查不存在残留引用。
- 迁移不是停用分组。组保持active时用户仍可能重新选择；旧请求继续按入站时的快照完成，不中断存量连接。
